Ports and Adapters (Simplified)

Today I’m gonna talk again about Ports and Adapters. In the past I’ve already written about Clean Architecture and Ports and Adapters, but today I would like to write about a pragmatic way to follow Ports and Adapters, simplifying it even more.

Overview

As you can see from the picture we have the following elements:

  • Domain: Is the code to keep decoupled and protected from external entities. Contains types, core logic functions, and ports.
  • Ports: Are the APIs (interfaces) defined within the domain that abstract external dependencies or the moving parts (like databases, emailers).
  • Adapters: Are the concrete implementations of a port, often tied to a specific technology (e.g., Express, DynamoDB, SES).

Some important notes:

  • All the Ports stay inside the Domain, they are part of it!
  • An Adapter exists only to implement a Port.
  • The structure enhances testability, as adapters implementing specific ports can easily be replaced with mocks or test doubles.
  • Dependencies flow inwards: Adapters depend on Domain Ports, but the Domain must not depend on any specific Adapter.
  • Dependencies are passed using Env pattern, making dependency injection explicit and type-safe.

Example

Imagine a service that manages users. This is the structure it could have:

src
├── adapters
│   ├── aws
│   │   └── ses
│   │       └── email-mailer.ts
│   ├── console
│   │   └── logger.ts
│   ├── express
│   │   ├── app.ts
│   │   └── register-users.ts
│   └── map
│       └── users-repository.ts
├── domain
│   ├── email.ts
│   ├── logger.ts
│   └── users.ts
├── config.ts
└── main.ts

Adapters are organized by technology first, then potentially by the port they implement. I found this structure coherent with the aims of adapters (create an implementation for a port or a way to interact with it using a specific technology). Moreover, it is super easy to find the right collocation for a new adapter.

Domain is simple. Each file contains related types, functions, and the ports needed by those functions.

The main is the glue of the system. It is the entry-point, and acts as the composition root where all the adapters are created and wired to make the system work.

The config file handles loading and providing configuration values (like API keys, database connection details) needed by adapters during initialization in main.

And the missing parts of Ports and Adapters?

As you already noted there is no explicit use-cases folder and no distinction between primary/secondary ports and adapters. Why?

Use Cases Folder

I keep use-cases inside the domain, they are functions of the domain. I did not find a consistent advantage in keeping use cases in a separate folder away from the domain types and ports they operate on, especially in moderately sized applications. It often felt like premature complexity.

If one domain file becomes too complex, it can then be split as needed. For many projects, placing the use case function directly in the relevant domain file (e.g., registerUser within users.ts) reduced boilerplate and kept related logic physically closer, improving discoverability.

Primary/Secondary Distinction

The formal distinction rarely impacted the actual implementation structure in a meaningful way for my projects. The direction of interaction (driving vs. driven) was usually clear from the context (e.g., an HTTP handler drives the application, a database repository is driven by the application). Omitting the labels simplified the vocabulary without losing practical clarity.

This approach prioritizes simplicity and reduces ceremony, which aligns with the Simple is beautiful principle.

Domain code

// file src/domain/users.ts
import { EmailEnv } from './email.js';
import { LoggerEnv } from './logger.js';

// UserEnv contains all the ports needed by the user domain functions.
export type UserEnv {
  userRepository: {
    insert: (definition: UserDefinition) => Promise<User>;
  };
}

export type User {
  // Using a branded type 
  // (e.g., type UserId = string & { __brand: 'UserId' })
  // offers more type safety but `string` is used here for simplicity.
  id: string;
  firstName: string;
  lastName: string;
  // the email is string for simplicity
  email: string;
  age: number;
}

export type UserDefinition = Omit<User, 'id'>;

// This is a domain function (acting as the use case) that,
// given the required environment (ports) and a user definition,
// registers a user.
export const registerUser =
  (definition: UserDefinition) =>
  // It requires an environment that satisfies UserEnv, EmailEnv and LoggerEnv
  async (env: UserEnv & EmailEnv & LoggerEnv): Promise<User> => {
    // Persist the user using the repository port
    // Error handling omitted for brevity
    const user = await env.userRepository.insert(definition);
    env.logger.log(`User inserted with ID: ${user.id}`);

    // Send a welcome email using the mailer port
    const email = { to: user.email, body: `Welcome, ${user.firstName}!` };
    await env.mailer.send(email);
    env.logger.log(`Welcome email sent to: ${user.email}`);

    return user;
  };

Note: The Env pattern (e.g. UserEnv) groups the required dependencies (ports) for domain functions, making dependency injection explicit and type-safe.

Adapters code

// file src/adapters/express/register-user.ts
import express from 'express';
import { RegisterUserBodyCodec } from './codec.js';
import { registerUser } from '../../domain/users.js';
import { AppEnv } from './app.js';

export const makeRegisterUserHandler =
  (env: AppEnv) => async (req: express.Request, res: express.Response) => {
    // RegisterUserBodyCodec is used here for
    // validating and parsing the incoming request body,
    // often implemented using a library like Zod or io-ts. 
    const result = RegisterUserBodyCodec.safeParse(req.body);

    if (result.success) {
      const user = await registerUser(result.data)(env);
      res.json(user);
    } else {
      const response = { error: result.error.issues };
      res.status(400).json(response);
    }
  };
// file src/adapters/express/app.ts
import express from 'express';
import { makeRegisterUserHandler } from './register-users.js';
import { LoggerEnv } from '../../domain/logger.js';
import { UserEnv } from '../../domain/users.js';
import { EmailEnv } from '../../domain/email.js';
import { Config } from '../../config.js';

export type AppEnv = LoggerEnv & UserEnv & EmailEnv;

export const makeApp = (config: Config, env: AppEnv) => {
  const app = express();
  const { port } = config.server;

  app.use(express.json());

  app.post('/users', makeRegisterUserHandler(env));

  return {
    start: () => {
      app.listen(port, () => {
        env.logger.log(`Example app listening on port ${port}`);
      });
    },
  };
};
// file src/adapters/map/users-repository.ts
import { User, UserEnv } from '../../domain/users.js';

export const makeUserRepository = (
  map: ReadonlyMap<User['id'], User> = new Map(),
): UserEnv['userRepository'] => {
  const db = new Map(map);
  return {
    insert: async (definition) => {
      const id = crypto.randomUUID();
      const user = { id, ...definition };
      db.set(id, user);
      return user;
    },
  };
};

Main code

// file src/main.ts
import { makeUserRepository } from './adapters/map/users-repository.js';
import { makeLogger } from './adapters/console/logger.js';
import { makeMailer } from './adapters/aws/ses/email-mailer.js';
import { makeApp } from './adapters/express/app.js';
import { loadConfigOrThrow } from './config.js';

const config = loadConfigOrThrow(process.env);

// create the adapters
const logger = makeLogger();
const userRepository = makeUserRepository();
const mailer = makeMailer(logger);

const env = {
  userRepository,
  mailer,
  logger,
};

// create the app
const app = makeApp(config, env);

// start the app
app.start();

Final Words

The Ports and Adapters pattern is a powerful tool for decoupling, but like any tool, its value lies in how and when you use it. My pragmatic approach is not about cutting corners, it’s about trimming perceived unnecessary complexity for the sake of clarity and potentially faster delivery in certain contexts.

Potential Trade-offs: Be mindful that in very large or complex applications, the lack of explicit use case separation might eventually lead to larger domain files that need refactoring. Similarly, while the primary/secondary distinction might feel like overhead initially, it could provide clarity in systems with many integration points. But I don’t think so so far.

To my future self: remember that simplicity scales. Start simple, apply patterns judiciously, and refactor towards more structure only when the complexity genuinely demands it. It’s all about finding the balance that works for your team, your project’s current scale, and its anticipated evolution.
